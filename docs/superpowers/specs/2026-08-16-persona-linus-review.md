# Linus Review:2026-08-16 Persona & Rules 设计

> 审查对象:`2026-08-16-persona-rules-design.md` · 五层分析 + 结论

---

## 三问

1. **真问题还是想象的问题?** 真问题。system prompt 硬编码在三处,换语气要重编译,内部 review §7.5 已标记。第二次出现同样的问题报告,说明它不会自己消失。
2. **有没有更简单的方法?** 有,而且方案就是它:把一个硬编码字符串换成"读几个 markdown 文件按固定顺序拼起来"。没有 schema、没有引擎、没有新协议。
3. **会破坏什么?** 公共 API 零变化;默认路径只多一行尾行(已声明)。子代理、压缩、缓存前缀全部不受影响。

## 五层分析

### 层 1:数据结构

核心数据 = `system_prompt: String`,由四个确定性来源拼接:persona 文件 → rules 文件 ×2 → skills 目录 → 固定尾行。所有权清晰:文件是用户的数据,compose 是纯函数,`Host` 持有结果 String 不变。没有新状态、没有运行时变更、没有复制风暴(构造时拼一次)。

对照反例:Open WebUI 的三层 persona(account/model/chat)+ DB 存储,是为多用户多模型发明的状态机。单用户自托管抄它就是抄别人的复杂度。这里没抄,对。

### 层 2:特殊情况

逐一过分支,判断是真实业务还是坏设计的补丁:

| 分支 | 判定 |
|---|---|
| persona 缺失 → 内置默认串 | 真实:默认行为必须零配置可用 |
| 项目同名覆盖全局 | 真实:与 skills 既有语义一致,不是新发明 |
| 名字非法(`..`/`/`)→ 警告 + 回退 | 真实:路径穿越是攻击面,不是假想 |
| 名字不存在 → 警告 + 回退 | 真实:打错字不应让助理起不来;警告必须列出查过的路径,否则"为什么人格没生效"会变成幽灵 bug |
| 空文件视为缺失 | 真实:`touch` 出来的空文件不该吞掉默认串 |
| rules 有/无 ×2 | 用"有才追加"消除,没有 if-else 树 |

没有为坏数据模型打补丁的分支。警告消息的具体格式已写进 spec(§4.2),不会实现时随手发挥。

### 层 3:复杂度审计

一句话本质:**把 system prompt 从硬编码字符串变成"persona 文件 + 规则文件 + skills 目录"的确定序拼接**。

新增概念:persona 文件、rules 文件、`GASKET_PERSONA` 旋钮、一个纯函数。四个,每个都有独立职责且砍掉任何一个都会伤功能(曾考虑砍 rules 并入 persona——换 persona 丢规则,语义错;曾考虑只留 env 内联——多行引号地狱,已被否决)。

实现 ~120 行含测试,体量对标 `skills.rs`。不能再砍半:再砍就是"只有一个 env 变量"的原始方案,满足不了"可自定义可扩展"的诉求。

### 层 4:破坏性

- `Host::new` 签名不动;`StreamFn`/WS/REST 协议不动;`.env` 无新必填项。
- 默认输出与现状差异 = 一行防注入尾行。这不是破坏 userspace,是给所有用户免费修一个真实攻击面(gasket 有 `fetch`/`bash`,工具输出混指令是现实威胁)。已显式声明,不是偷偷加的。
- 三个 call site 一次性切换,不留旧路径。
- 组合顺序固定 → Anthropic ephemeral cache 前缀继续命中;不加这个设计反而会因顺序漂移破坏缓存。

### 层 5:实际性

个人助理每天每轮都过 system prompt,人格/规则是使用频率 100% 的配置面。复杂度(几个 md 文件 + 一个纯函数)与问题严重度(当前为零可配置性)匹配。硬约束正确地留给了已有的 hooks/permission/sandbox,没有在 prompt 层重复造执行引擎——这是本方案最值得肯定的一条边界。

## 输出

```
【品味评分】
好品味 —— 数据结构(纯函数拼接确定性来源)对了,特殊情况都在消灭而非堆砌,
复杂度与问题匹配,零破坏。警告消息具体到路径、名字白名单防穿越、组合顺序
保缓存,这三处细节说明设计者想过实现之后的事。

【致命问题】
无。以下两条在 review 中被发现并已折入 spec,不再是问题:
- GASKET_PERSONA 路径穿越 → 名字白名单 [A-Za-z0-9_-],非法视同未设置 + 警告
- persona 名字打错静默回退 → 警告必须列出查过的两个路径,可断言

【改进方向】
无阻断项。两个提醒(实现期注意,不改设计):
1. 尾行是新增的用户可见行为,usage.md 必须写明,不能只活在 spec 里。
2. compose 在 Host 构造时执行一次,"改文件要重启"要写进文档,否则会被当 bug 报。

【核心判断】
值得做:真问题(硬编码,已被标记两次)、真简单(纯函数 + markdown 文件)、
真零破坏(API 不动、默认行为只多一行已声明的加固)。

【关键洞察】
- 数据结构:system_prompt 是"persona(可替换身份)+ rules(恒定约束)+
  skills(按需目录)+ 尾行(框架加固)"的确定序拼接——四个来源一个顺序,无状态。
- 复杂度:可消除的复杂性已经消除(结构化 schema、三层 persona、执行引擎全部否决)。
- 风险点:最大风险不在设计而在文档——分层语义(全局/项目、覆盖/追加)如果
  usage.md 写不清,用户会把"项目覆盖全局 persona"和"rules 追加"搞混。

【Linus式方案】
1. 数据结构已对:纯函数 compose(cwd, global_root, persona) → String。
2. 特殊情况已消除:缺文件/空文件/非法名字统一走"回退 + 可断言警告"。
3. 最笨最清晰:读文件、拼字符串、警告打 stderr。不引入解析器。
4. 零破坏:API、协议、默认路径(除已声明的一行)全部不动。
```
